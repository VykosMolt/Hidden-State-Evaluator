## 2. THE FINDING — read this first

**bf16 inflates the transport measurement `rho` by ~62%.**

Measured on a real B300, 6 validation tasks, alpha 0.04, axis 1, same engine,
identical inputs — only the model dtype differs:

| task | rho (bf16) | rho (fp32) | inflation |
|---|---|---|---|
| b200val-000 | 3.6245 | 2.4017 | +50.9% |
| b200val-001 | 3.8252 | 2.3645 | +61.8% |
| b200val-002 | 3.8649 | 2.3893 | +61.8% |
| b200val-003 | 3.7316 | 2.2825 | +63.5% |
| b200val-004 | 4.2506 | 2.4248 | +75.3% |
| b200val-005 | 3.8678 | 2.4327 | +59.0% |

Mechanism: `rho = RMS(h_int - h_base) / injected_rms` is a difference of two
nearly-equal vectors. In bf16 the L4_47 boundary carries ~0.06–0.125
quantisation noise per element (1–2 ULP), which adds in quadrature to the real
signal, so the measured RMS is systematically LARGER than the true one. fp32's
noise floor is 2.8e-05 and the signal emerges.

This is independent of batching. Every rho this project has measured in bf16 —
serial included — is affected. A full run would have completed, passed its
gates, and produced numbers wrong in a direction nothing in the harness checks.

**Strength of evidence:** 6 tasks, one alpha, one axis. Effect is large and
consistent (50–75%, no exceptions) and the mechanism is understood, but this is
NOT yet paper-grade. Confirm across the alpha grid before relying on it.
Prediction to test: at alpha 0.005 the injected signal is 8x smaller, so the
contamination should be WORSE, not better. If it is not, the mechanism is wrong.

## 3. Settled today

**The calibration is batched.** The sealed orchestrator always accepted
`backend=` (`orchestrate_calibration`, `run_o1_v2_orchestrator.py`); only its
CLI omitted it, and `production_entry` drives it as a subprocess through that
CLI. `runner/calibration_launcher.py` is the missing CLI surface, OUTSIDE the
sealed package; `runner/calibration_backend.py` precomputes every enumerated row
through the equivalence-gated batched engine and serves the orchestrator's
synchronous `generate()` as a lookup. A key never precomputed RAISES — a silent
serial fallback would mix engines inside one record set. The sealed package is
untouched and byte-verified.

**Enumeration is exact.** `enumerate_calibration_groups` was replayed against
the sealed loop on real inputs: 4608 vs 4608, order identical, 0 missing, 0
extra.

**Gates test what their names say** (`438d529`). They were wired to
`scientific_core_identical`, which compares generated text — unsatisfiable for
any batched config on hardware. They now test the frozen tolerances that
`compare_o1_backends` has always computed and NOTHING read:
`action_seed_mapping_exact` → identity mapping; `intervention_pass` →
`injected_rms` within tolerance; `transport_pass` → rho within tolerance.
Missing measurement or missing tolerance is NOT a pass.

**The batched engine is faithful at batch 1.** `generate_batch(B=1)` produces a
bit-identical boundary to the sealed `generate_branch`. The whole discrepancy is
batch shape, not engine identity.

**Measured hardware numbers** (B300 SXM6 AC, $7.89/h):

- serial decode: `s/row = 0.172 + 0.16231 * tokens` → **6.16 tok/s** at batch 1.
  Prefill overhead ~0.1 s; cost is essentially pure per-token.
  The B300 is NOT faster per row than a laptop (6.7 tok/s). All its advantage is
  batch parallelism, which the serial orchestrator cannot use.
- generated tokens over 576 calibration-shaped rows: **median 148, mean 211.7,
  p90 448, max 448 (the cap), min 13**.
- batched generation, mixed 192-row batches: **5,348 rows/h**.
- FL LoRA training: 288 trainable tensors, 12.19M params, **0.962 s/update**
  (flat across seq 256/512 at `fl_max_tokens_per_batch=2048`), peak 52.7 GB.
  6,000 updates = **1.60 h = $12.65**.
- checkpoint fetch 11–16 s; GHCR image pull ~3.5 min; provisioning ~4 min total.

## 4. NOT settled

**fp32 cost is unmeasured.** This is the blocker for pricing. The timings from
the precision pod are useless — the bf16 arm took 78 s and fp32 17 s purely
because the first sweep absorbed warmup. fp32 doubles weights (5.2→10.4 GB) and
activations. Need a clean throughput measurement before the session can be
priced. **~$1.50 pod.**

**Tolerance is unset.** 1e-6 was never achievable on hardware and was never
validated against it. fp32 batch-shape sensitivity is 2.398e-05 worst case
against an effect size of ~2.4 — one part in 100,000. Something like **1e-4** is
both achievable and meaningful. This is a scientific decision, not a code one.

**b256 has no equivalence verdict.** The fast path is ENABLED, not EARNED.
`calibration_backend_choice` falls back to REFERENCE_SERIAL until the gates
actually pass. Local synthetic equivalence (full 384-row corpus, batches 8/16/256)
passes every gate — but that is a CPU run against a fake model and says nothing
about numerics; that is exactly the trap that produced the wrong conclusion
mid-session.

**Does the session fit?** At bf16 rates: reference pass 384 rows serial = 3.68 h
= $29, calibration batched = 0.86 h = $6.80, FL = 1.60 h = $12.62, overhead =
0.32 h = $2.50 → **6.46 h / $51**, over the frozen 5.07 h / $40 cap. Levers, all
of which the user has said are NOT set in stone: shrink the equivalence corpus
(a task subset is already supported), raise the cap, or raise
`o1_timeout_seconds`. With a 128-row reference the total is ~4.0 h / ~$32.

## 6. Operational notes worth keeping

- **Always dry-run the call chain locally before renting.** Three pods were
  wasted earlier on invocation bugs (missing args, wrong `repo_type`, file path
  instead of `-m`). Signatures can be checked for free with `inspect.signature`.
- **Put pod Python in a QUOTED heredoc** (`<<'PYEOF'`), never inside a
  double-quoted `-c` string. Shell expansion silently corrupted one script.
- **Do not pipe pod output through `tail`** — it buffers, and you go blind until
  the process exits. Two runs were unobservable because of this.
- **The pod script ends in `sleep infinity` on purpose**, so nothing stops
  billing but the watchdog. `lab_watchdog.sh` terminates on the completion marker
  or at a hard cap. Keep it armed; update the marker name per run.
- **`lab_rent.sh` reads the digest from `RUNPOD_SESSION_CONFIG.json` and
  pre-flights it against GHCR.** A hardcoded, since-deleted digest killed a pod
  one second after creation. Never hardcode it again.
- **Importing sealed modules writes `__pycache__` into the sealed dir**, which
  `verify_sealed_modules` then refuses. Always set `PYTHONDONTWRITEBYTECODE=1`.
- **Regenerate transfer manifests after ANY source change**
  (`python -m o1_b200.runner.make_transfer_manifest`), or `ARTIFACT_VERIFY` fails
  — on the pod, after you have paid to get there.
- The FL lock asserts CORRESPONDENCE with the O1 build record, not a literal
  tag. `image_name`, `image_id_local` and `foundation_learner_source_sha256` must
  all match, and it caught a partial rebind today.
