### What was observed on 2026-08-27 (historical)

Four pods, three GPU classes (B300, B200, RTX 4000 Ada), several datacenters,
anonymous **and** authenticated: the container never started.

- Anonymous starts ~1.6 MB/s per layer (~3.2 MB/s aggregate), **decays to
  ~0.12 MB/s, and restarts layers mid-transfer** — the progress denominators
  change (2.855 GB → 2.362 GB).
- Authenticated (`POST /containerregistryauth` + `containerRegistryAuthId`,
  PAT `VykosMolt`) emitted **no progress lines at all** for 1500 s. No 401/403.
  Authentication does not help.

**It is not the image, and not RunPod.** The two stalling layers are
`69d8add51e8f` (2.85 GB) and `d4928eebad23` (2.77 GB) — 99% of a 5.67 GB image —
and they are **byte-identical to v0.3.12's**, which RunPod pulled in ~3.5 min on
2026-08-24. They range-GET from the workstation at ~5 MB/s (HTTP 206).

**Control experiment (decisive).** `qwen38pod up` on a B300 in EU-NL-1 pulled and
*extracted* `runpod/pytorch:…` — **~20 GB, 3.5× larger** — in about 5 minutes,
same provider, same GPU type. Pod acquisition, the account, the B300 pool and
RunPod's image fetching are all healthy. **The fault is specific to ghcr.io.**

Full evidence: `~/.local/share/o1-b300-lab/BASELINE_ANON.txt`.

### The fix, and its one consequence

`~/.local/share/o1-b300-lab/mirror_image.sh` mirrors the bound image to a second
registry. The image is still in the local Docker cache as `b50a64c733fd` — which
IS the bound manifest digest — so nothing is rebuilt and the content cannot
drift. The script refuses to report success unless the pushed digest still
equals `sha256:b50a64c7…`. It needs `DEST_REPO` and a logged-in registry
(`docker login`); only `ghcr.io` is authenticated on this machine today.

**`image_digest_ref` contains the registry HOST and is deployment identity.**
For the lab probe, pass `lab_rent.py --image <mirror-ref>` and touch no config.
For the real calibration session, rebinding is a change to the authorized
deployment spec — a recorded decision, not a side effect of routing around an
outage. Note this problem was going to hit the real session too, at $7.89/h with

## 4. Corrections to my own earlier claims

- **"The pulls were stuck."** They were slow. I read `Retrying in N seconds` as a
  failure loop without ever looking at a byte counter, and killed attempt 1 at
  28 min when it may have been close to done. Then I bounded attempt 2 with a
  420 s pull guard derived from the remembered "216 s" — which described
  **v0.3.12 on a possibly warm machine**, not this image. It killed a working
  pull at 7 min. **USD 4.64 of today's spend is those two premature
  terminations.** Watch the byte counter, not the retry lines; never bound a
  wait with a figure you have not measured on the artifact in hand.
- **"The image is 13.8 GB."** That is the *uncompressed* size. It is **5.67 GB
  compressed**, which is what governs pull time.
- **"EU-NL-1 has dropped out for B300."** Wrong. The preflight's
  `compatible_datacenters` listed only EUR-IS-1/US-WA-2 at 10:05Z, but RunPod
  placed a B300 in **EU-NL-1** at 14:14Z. That list is not exhaustive for
  placement. Worth watching: `quote_instance` pins `sorted(datacenters)[0]`, so
  it can pin a datacenter that is not where capacity is.
- **"v0.3.17 was never proven pullable."** True but immaterial — the layers that
  stall are shared with v0.3.12 and were proven pullable.

## 5. RunPod API traps (each cost real time)

- **Logs are v2-only, and SSE.** `api.runpod.io/v2/pods/{id}/logs?source=container`.
  `rest.runpod.io/v1` has **no `/logs` path** and 400s. This had the watchdog
  silently blind for a whole rental. The stream stays open after replaying the
  tail, so read it with a deadline — `lab_common.logs_v2` shells to
  `curl --max-time` because urllib around a never-EOF response was unreliable.
- **Pod creation with `dockerEntrypoint`/`dockerStartCmd` is v1 only.** REST v2
  has just `args`, which cannot replace the image ENTRYPOINT (`start_b300.sh`,
  which would run the whole production state machine).
- **v1 enums are narrower than the v2 catalog.** `allowedCudaVersions` tops out
  at `"13.0"` and rejects `"13.2"`; `dataCenterIds` knows `US-WA-1`, not
  `US-WA-2`. Both rejections are 400s at create time.
- **GraphQL needs a `User-Agent`** or Cloudflare returns `error code: 1010`, and
  `clientBalance` needs the write-capable key (line 3 of `fidelio.txt`); line 1
  is read-only and 403s on POST.

## 6. The probe — built, validated, never run on a GPU

`~/.local/share/o1-b300-lab/probe.py`. Answers all three open blockers from
`HANDOFF_2026-08-24.md` §4/§5 in one rental:

- **Arm A** — rho across the **frozen** alpha grid `[0.005…0.08]` (read from
  `corpus/CORPUS_CONFIG.json`, not invented), bf16 vs fp32, 6 tasks, axis 1.
  Prefill-only: the L4_47 boundary is captured during prefill, so the sealed
  function's 448-token decode is pure cost for this measurement. Imports the
  sealed `OneShotResidualEdit` and `downstream_delta_rms` — the arithmetic under
  test is the real arithmetic.
- **Arm B** — fp32 cost: batch-1 decode and batched rows/h at 16/64/256 with full
  256-token rows, peak HBM, OOM ceiling. Warmed with a discarded pass first,
  because the 2026-08-24 fp32-vs-bf16 timings were meaningless for exactly that
  reason.
- **Arm C** — whether dtype changes generated text / parsed answer / verifier
  verdict. This sizes the amendment: if it does, the reference pass must be
  recomputed in fp32 and the equivalence gates compare fp32-against-fp32.

**The fp32 loader is textually parallel to the sealed `_load_model` and differs
in exactly one token (`torch_dtype`)**, so the comparison isolates dtype.

**The dtype is inside the seal.** `run_o1_v2_generation.py:121` hard-codes
`torch_dtype=torch.bfloat16`, and every science path reaches it —
`backends.py:49 load_model_artifact` just calls the sealed `_load_model`. fp32 is
not a flag anyone can set. It needs either a re-seal or an outside-the-seal
loader override at that seam, and unlike amendment 4's backend injection (which
the gates certify as bitwise-identical) **a dtype change deliberately alters the
numbers, including the reference the gates compare against.** That is a
scientific amendment.

Validated locally end to end on the synthetic runtime: every sealed signature
checked with `inspect.signature`, the HF fetch round-trip returns the exact sha
the pod asserts, every CLI flag confirmed to exist. The dry run also caught a
real defect — a **null** result printed `CONSISTENT`, because monotonicity is
satisfied trivially by all-zeros. The verdict now requires a material effect,
and there is a sharper test: if bf16 adds an alpha-independent noise floor `n`,
then `n = injected_rms · √(ρ_bf16² − ρ_fp32²)` is **constant** across a 16× span
of alpha. Monotone inflation fits many stories; a flat `n` fits essentially one.
